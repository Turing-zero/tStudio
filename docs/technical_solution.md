# 四足巡检机器人平台技术方案书

## 1. 项目背景与目标
构建一套面向四足机器人的综合巡检管理平台，实现对多台机器人的实时监控、遥操作、任务调度、AI 告警分析及全生命周期运维管理。平台需具备高实时性、高可靠性及良好的扩展性，支持从单机测试到多机商用的平滑演进。

### 1.1 核心设计原则
*   轻量起步，弹性扩展：优先满足交付与稳定性，在容量到达瓶颈后再引入更重的计算/中间件。
*   端-边-云协同：机器人端保证控制闭环，云端保证任务、告警、资产与审计的统一管理。
*   实时性优先：监控与遥操作链路端到端可观测，优先保证低延迟与可恢复。
*   解耦与可运维：设备接入、业务处理、AI 分析、通知告警解耦，支持灰度与回滚。

## 2. 总体架构设计
采用 **端-边-云** 分层架构，确保数据流的高效传输与处理。

### 2.1 逻辑架构图
```mermaid
graph TD
    User[用户终端 (PC/Pad/大屏)] -->|HTTPS/WSS| LB[负载均衡/Nginx]
    
    subgraph Cloud[云端业务平台]
        LB --> Frontend[前端应用 (React/Three.js)]
        LB --> Backend[后端服务 (FastAPI)]
        LB --> MediaServer[流媒体服务 (SRS/ZLMediaKit)]
        LB --> MQTTBroker[消息网关 (EMQX)]
        
        Backend --> DB[(PostgreSQL)]
        Backend --> Redis[(Redis)]
        Backend --> TSDB[(InfluxDB/Timescale)]
        Backend --> MinIO[(MinIO 对象存储)]
        Backend --> AI[AI 分析服务]
    end
    
    subgraph Edge[机器人边缘端]
        RobotCore[机器人核心控制 (ROS2)] -->|MQTT| MQTTBroker
        RobotCore -->|RTMP/SRT| MediaServer
        RobotCore -->|HTTP| Backend
        AI_Edge[边缘 AI (Jetson)] --> RobotCore
    end
```

*   若文档平台不支持 Mermaid，可按以下文字拓扑理解：
    *   用户端通过 HTTPS/WSS 访问 Nginx/网关。
    *   网关转发到前端静态站点与后端 API/WebSocket。
    *   机器人通过 MQTT 接入 EMQX，上报状态与告警；后端订阅并落库、推送前端。
    *   视频通过机器人推流到流媒体服务，前端以 WebRTC 低延迟播放。
    *   文件与媒体存 MinIO；业务数据存 PostgreSQL；高频时序存 InfluxDB/Timescale；热点状态与会话放 Redis。

### 2.2 核心技术栈选型

| 模块 | 推荐技术 | 选型理由 |
|---|---|---|
|前端|React + TypeScript + Three.js|生态成熟，Three.js 支持 3D 场景与点云渲染|
|后端|FastAPI (Python)|高性能异步框架，原生支持 WebSocket，易集成 AI|
|通信|EMQX (MQTT)|物联网标准协议，弱网稳定，支持海量设备接入|

|数据库|PostgreSQL + InfluxDB|PG 业务关系；InfluxDB 存轨迹、电量等时序数据|
|存储|MinIO|S3 兼容，私有化部署，存图片、地图包、OTA 固件|
|部署|Docker Compose / K8s|容器化交付，单机编排到集群平滑演进|

### 2.4 关键技术方案补充（面向生产交付）
*   通信：ROS Bridge + MQTT 并存
    *   ROS Bridge：适合局域网调试、开发期可视化订阅；可继续保留用于研发模式与单机演示。
    *   MQTT（EMQX）：生产主通道，适合公网/弱网/海量设备；状态上报、任务下发、告警事件建议走 MQTT。
*   视频：WebRTC 低延迟 + HLS 回放
    *   监控与远程接管：WebRTC（毫秒级延迟）。
    *   告警取证与历史回看：HLS/MP4（分钟级切片/文件回放）。
    *   流媒体服务建议：SRS 或 ZLMediaKit（具备 WebRTC 能力）。
*   异步任务：Celery（或 RQ）处理重任务
    *   AI 二次识别、报表生成、媒体转码、批量导入/导出、告警通知等，避免阻塞 API。
    *   使用 Redis/RabbitMQ 作为队列后端（根据吞吐与可靠性选择）。
*   数据存储：PostgreSQL + 时序库 + MinIO
    *   PostgreSQL：任务、路线、资产、告警、用户权限、审计。
    *   InfluxDB/Timescale：轨迹、电量、温度、网络质量等高频数据。
    *   MinIO：地图包、点云、截图、告警视频片段、OTA 固件与校验信息。
*   权限与审计：RBAC + 操作留痕
    *   前端功能点与 API 权限统一控制；重要操作（急停/接管/OTA/删除任务）记录审计日志。
*   可观测性：日志 + 指标 + 链路
    *   日志：Loki/ELK 二选一（MVP 可先本地文件 + 轮转）。
    *   指标：Prometheus + Grafana（或轻量替代）监控 API、MQTT、流媒体、数据库。

### 2.5 其他技术引入决策（什么时候需要 Kafka/Flink/Java/K8s）
*   Kafka：当设备/事件量进入“持续高吞吐”且需要多消费组独立处理时再引入；当前阶段可用 RabbitMQ/Redis Stream 够用。
*   Flink：当需要实时流计算（秒级聚合、复杂 CEP、窗口计算）且数据规模很大时才引入；MVP/单园区通常不需要。
*   Java 微服务：当团队已有成熟 Java 体系与治理平台，或需要复杂的企业集成（ESB/多租户/合规）再考虑拆分；当前 FastAPI 足以快速交付。
*   K8s：当需要多环境（dev/test/prod）一致部署、高可用、弹性扩缩与灰度发布时上 K8s；交付期可先 Docker Compose。

### 2.6 数据库选型对比（机器人业务视角）
在机器人平台业务中，PostgreSQL 的扩展能力（PostGIS、TimescaleDB、JSONB）对“空间数据 + 时序数据 + 异构设备配置”更友好，适合作为业务主库。

| 特性 | PostgreSQL（推荐） | MySQL | 对机器人业务的意义 |
|---|---|---|---|
| 空间数据（GIS） | PostGIS（能力强） | 基础支持 | 处理 3D/2D 坐标、禁入区围栏检测、路径点位计算、楼层区域检索 |
| 时序数据 | TimescaleDB（原生扩展） | 通常需外挂组件 | 存储每秒上报的电量、姿态、温度、网络质量等高频采样数据 |
| 非结构化数据 | JSONB（可索引） | JSON（索引与查询能力较弱） | 存储不同型号机器人上报的非统一配置、能力集与扩展字段 |
| 并发模型 | MVCC（读写互不阻塞） | 依场景不同 | 支撑大量机器人同时上报状态与大屏高频查询，降低读写互相影响 |

建议落地方式：
*   PostgreSQL 作为业务主库：任务、路线、告警、资产、用户权限与审计。
*   PostGIS 作为空间能力：地图区域、禁入区、多楼层点位与拓扑查询。
*   TimescaleDB 作为时序扩展（可选）：轨迹、电量、姿态、温度、网络等高频数据；若暂不引入，可先按天分表或使用 InfluxDB。

### 2.7 PostgreSQL 进一步优势（落地视角）
*   空间查询与索引能力成熟：PostGIS + GiST/SP-GiST 索引，适合做禁入区/围栏（ST_Intersects、ST_DWithin）、楼层区域检索与路径点位计算。
*   面向高频写入的时序优化路径清晰：可用 TimescaleDB（Hypertable/压缩/连续聚合），或先用原生分区表 + BRIN 索引按天/月滚动。
*   JSONB 更适配异构设备上报：JSONB + GIN 索引，能在“字段不固定”的前提下稳定查询与过滤（不同型号能力集、参数扩展字段）。
*   并发与一致性更稳：MVCC + 行级锁适合“机器人高频上报 + 大屏高频查询”并行；任务调度类场景可用 advisory lock 避免重复派发。
*   高可用与备份体系成熟：流复制主从、自动故障切换（如 Patroni），配合全量备份 + WAL 归档实现 PITR（按时间点恢复）。
*   横向扩展手段完整：读写分离（只读副本承担查询）、连接池（PgBouncer）、分区与索引策略优化，支撑业务增长的平滑演进。

## 3. 核心功能模块详细设计

### 3.1 总览大屏 (Dashboard)
*   **功能**：展示在线率、任务进度、核心告警、实时地图分布。
*   **实现**：
    *   前端通过 WebSocket 订阅 Redis 中的实时聚合统计信息。
    *   地图组件加载 GeoJSON/PCD 数据，叠加机器人实时坐标（经纬度/局部坐标）。

### 3.2 机器人实时监控与遥操作
*   **状态同步**：机器人通过 MQTT (`/robot/{id}/status`) 上报频率 1-5Hz 的状态包（位置、电量、欧拉角）。
*   **视频流**：机器人端 GStreamer 推流 -> SRS 转 WebRTC -> 前端播放器。
*   **控制指令**：前端虚拟摇杆 -> API/MQTT (`/robot/{id}/cmd_vel`) -> 机器人执行。
    *   *安全机制*：后端增加指令看门狗，超时自动下发急停。

### 3.3 巡检任务与路线管理
*   **路线编辑**：基于 Three.js 的 3D 场景，用户点击地面生成 Waypoints，支持拖拽调整。
*   **数据结构**：

```json
{
  "task_id": "uuid",
  "route": [
    {"x": 1.0, "y": 2.0, "action": "photo", "params": {}},
    {"x": 5.0, "y": 5.0, "action": "wait", "params": {"duration": 5}}
  ]
}
```

*   **调度引擎**：使用 `APScheduler` 或 `Celery Beat` 定时触发任务下发。

### 3.4 地图与场景管理
*   **地图上传**：支持上传 `.pcd` (点云) 或 `.pgm` (栅格) 地图。
*   **切片加载**：对于超大点云，后端预处理为 Potree 格式或八叉树结构，前端按需加载，保证流畅度。
*   **多楼层**：数据库设计 `floor_id`，前端通过下拉框切换不同点云底图。

### 3.5 AI 识别与告警中心
*   **边缘 AI (推荐)**：机器人搭载 Jetson Orin，本地运行 YOLOv8，识别到火焰/人入侵后，仅上传报警图片和元数据（节省流量）。
*   **云端 AI (补充)**：对于复杂场景，上传短视频片段到云端进行二次深度分析。
*   **告警推送**：后端写入数据库 -> 触发 WebSocket 通知前端弹窗 -> 调用短信/钉钉接口通知运维。

### 3.6 系统与运维管理
*   **OTA 升级**：
    1. 管理员上传固件包至 MinIO。
    2. 后端发布 MQTT 升级指令（含下载 URL 和 MD5）。
    3. 机器人下载 -> 校验 -> 重启 -> 上报新版本号。
*   **日志回放**：记录机器人所有上报的状态数据（时序数据库），前端支持按时间轴回放轨迹和仪表盘状态。

## 4. 交付与部署方案
*   **MVP 阶段 (快速交付)**：
    提供 `docker-compose.yml` 文件，一键拉起 Nginx, FastAPI, MinIO, EMQX, Postgres, Redis 等所有服务。
*   **生产阶段 (高可用)**：
    *   数据库采用主从复制。
    *   后端服务无状态化，通过 K8s Deployment 扩容。
    *   EMQX 集群化部署，保证消息高吞吐。

### 4.1 私有化交付硬件配置建议（局域网服务器）
根据机器人接入规模，建议采用以下硬件规格进行私有化交付：

| 规格名称 | 适用规模 | 核心配置建议 |
|---|---|---|
| 生产型（Standard） | 3–5 台机器人 | CPU：Xeon Silver 4410Y；GPU：RTX 4080（16G）；RAM：64G ECC |
| 高性能型（Advanced） | 5–10 台及以上/集群 | CPU：双路 Xeon Gold；GPU：A30 或 RTX 6000；RAM：128G+ ECC |

说明：
*   GPU 通常是关键组件之一，用于流媒体转码（如多路视频转封装/转码）与云端 AI 二次核验（如仪表读数、红外测温、外观缺陷复核）。
*   若视频与 AI 均在机器人端完成，云端 GPU 配置可下调；若云端需要承接多路视频与二次识别，需按并发路数与模型复杂度评估 GPU。

### 4.2 高可用与高并发：服务器与集群规划
生产环境为了避免单点故障（SPOF），建议至少 3 台服务器组成集群；预算充足时以 5 台为更稳妥的全组件冗余目标。

服务器数量建议：
*   3 台（最低可用）：关键组件做主从/集群，允许少数组件以“单实例 + 可恢复”为目标，满足可交付与可运维。
*   5 台（更推荐）：数据库、消息、流媒体、对象存储与可观测组件可实现更均衡的冗余与资源隔离。

3 台集群参考分布（可按资源与网络调整）：
| 节点 | 核心职责 | 典型服务 |
|---|---|---|
| Node-1（入口与计算） | 对外入口、无状态业务扩容位 | Nginx/Ingress、前端静态站点、后端 API（副本 1）、后台任务（副本 1） |
| Node-2（消息与主库） | 设备接入与写入优先 | EMQX（节点 1）、PostgreSQL 主库、Redis（主/Sentinel 之一） |
| Node-3（媒体与副本） | 视频与存储、读扩展 | 流媒体（SRS/ZLMediaKit）、PostgreSQL 只读副本、Redis（从/Sentinel 之一）、MinIO、监控与日志（Prometheus/Grafana/Loki） |

关键组件高可用要点：
*   入口层：双 Nginx/HAProxy + Keepalived（VIP）实现入口冗余；若上 K8s 则用 Ingress + 多副本 Service。
*   后端服务：保持无状态（会话/缓存/锁下沉到 Redis/数据库），用多副本水平扩容；异步任务与 API 分离部署避免互相拖慢。
*   MQTT（EMQX）：启用集群与持久会话，弱网断连可恢复；消息主题按机器人/站点规划，避免全量广播导致热点。
*   PostgreSQL：主从流复制 + 自动故障切换（如 Patroni）；读写分离后将大屏/报表查询优先走只读副本；定期备份并做恢复演练。
*   Redis：MVP 可用主从 + Sentinel；需要更高吞吐与多分片时再升级 Redis Cluster；重要队列任务建议选择具备持久化语义的方案或增加补偿机制。
*   对象存储：MinIO 生产建议分布式模式并开启版本控制；若 3 台难以满足磁盘数量与冗余约束，可用“MinIO 单实例 + 备份”过渡，后续再扩成分布式。
*   流媒体：多路并发时优先做横向扩容（多实例 + 负载均衡），录像文件落 MinIO；告警取证优先短片段，降低长期存储压力。

容量与演进建议：
*   MVP：Docker Compose 单机或 2 台（应用/数据分离）即可交付与试运行。
*   生产：优先将后端、MQTT、流媒体、数据库全部容器化并纳入统一编排（Docker Swarm 或 K8s），再逐步补齐全链路监控、备份与容灾。

## 5. 下一步实施计划
1.  **搭建基础环境**：部署 EMQX 和 MinIO，打通 MQTT 通信链路。
2.  **改造现有代码**：将 `roslibpy` 替换/封装为 MQTT Client，实现更稳定的公网通信。
3.  **集成视频流**：搭建 SRS 服务，测试 WebRTC 低延迟推流。
4.  **开发 3D 路线编辑器**：完善前端 Three.js 交互逻辑。

### 5.1 MVP → 商用演进路径
平台端开发资源：单人全栈（前端 + 后端 + 部署运维），机器人端多人但不计入本周期。以下周期按“可上线可运维”为口径评估，默认复用现有代码基础（React/FastAPI/ROS Bridge/MinIO）并优先交付核心闭环。

*   第一阶段（6–10 周，MVP 可演示可试运行）
    *   基础框架：统一配置、日志、鉴权雏形、基础部署脚本（单机/测试环境）
    *   实时监控：在线/离线、基础状态面板、2D/简化 3D 定位（单机器人优先）
    *   任务闭环：任务创建/下发/状态回传/失败原因记录（先跑通流程，策略先简化）
    *   告警闭环：告警入库、列表、确认/处理状态、与任务/点位关联（先不做复杂规则）
    *   视频接入（可选项）：优先接入已有视频源；若从零搭 WebRTC，周期增加 2–4 周
*   第二阶段（8–14 周，产品化可交付）
    *   路线编辑：Waypoints 编辑、停留/动作、参数下发与校验、版本管理
    *   地图/场景：地图列表、版本回滚、楼层切换与基础拓扑、点位/区域标注
    *   告警规则：区域启用、阈值与通知渠道配置，告警取证（截图/片段）与回看
    *   回放：轨迹回放、任务复盘、关键指标报表（基于时序数据）
    *   权限完善：RBAC、审计日志、关键操作二次确认与风控
*   第三阶段（12–24 周，规模化与行业方案）
    *   多机器人调度：轮换、容量管理、任务队列与优先级、异常复检
    *   多站点/多园区：多租户/多站点数据隔离、跨楼层/跨区域拓扑
    *   通信升级：引入 MQTT/EMQX 作为生产主通道（与 ROS Bridge 并存），弱网与断线重连优化
    *   商业化：AI 能力模块化、计费与授权、SLA 与运维体系（监控告警/备份恢复）
